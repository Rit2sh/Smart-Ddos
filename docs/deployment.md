# Deployment, Infrastructure & Operations Guide: Smart DDoS Shield

This guide covers production provisioning, environment configuration, reverse-proxy setup, health monitoring, secret management, upgrade procedures, and disaster recovery for Smart DDoS Shield.

---

## 1. Local Development via Docker Compose

Smart DDoS Shield includes a ready-to-run `docker-compose.yml` defining PostgreSQL 16 and Redis 7.

```bash
# 1. Start database containers
docker-compose up -d

# 2. Apply database schema via Prisma
npx prisma db push

# 3. Start Next.js development server
npm run dev
```

Containers exposed:
- **PostgreSQL**: `localhost:5432` (`smart_ddos_shield` database)
- **Redis**: `localhost:6379`

## 2. Production Multi-Stage Dockerfile

```dockerfile
# Stage 1: Dependencies
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

# Stage 2: Builder
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npx prisma generate
RUN npm run build

# Stage 3: Runner
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next ./.next
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package.json ./package.json

EXPOSE 3000
CMD ["npm", "start"]
```

## 4. Health & Readiness Probes (Kubernetes / ECS / ALB)

Smart DDoS Shield provides decoupled liveness and readiness endpoints:

### Liveness Probe (`/api/health`)
- **Path**: `GET /api/health`
- **Port**: `3000`
- **Interval**: 10s
- **Success Criteria**: HTTP 200 with runtime memory and uptime. Verifies control plane Node.js process is responsive.

### Readiness Probe (`/api/ready`)
- **Path**: `GET /api/ready`
- **Port**: `3000`
- **Interval**: 5s
- **Success Criteria**: HTTP 200. Checks PostgreSQL connectivity, collector heartbeat freshness (within 60s), and returns structured subsystem health.
- **Architectural Guarantee**: Decouples control-plane health from protected application attack status. An under-attack asset will NOT cause the platform readiness probe to fail.

## 5. Reverse-Proxy & NGINX Rate-Limiting Integration

Edge reverse proxies host the generated defensive rate-limiting zones:
```nginx
# Auto-generated by Smart DDoS Shield Policy Engine
limit_req_zone $binary_remote_addr zone=zone_pol_def_01:10m rate=500r/s;

location /api/v1/checkout {
    limit_req zone=zone_pol_def_01 burst=50 nodelay;
    limit_req_status 429;

    proxy_pass http://origin_upstream;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Shield-Policy-Id "pol_def_01";
}
```

## 6. Upgrade, Rollback & Disaster Recovery Procedures

### Rolling Zero-Downtime Upgrades
1. Apply database migrations: `npx prisma migrate deploy`
2. Deploy new container revision to Kubernetes / ECS cluster with rolling update (`maxSurge: 25%`, `maxUnavailable: 0`).
3. Verify `/api/ready` returns HTTP 200 across new pods before cutting traffic over.

### Policy Rollback Controls
1. If an operator enforces a rate-limiting policy that produces unexpected false positives, click **Rollback Policy to Baseline** in the incident dashboard or execute:
   `POST /api/v1/policies/:id/rollback`
2. The platform restores the known-good baseline reverse-proxy configuration and invalidates the edge rate-limiting zone within 2.5 seconds.

### Database Backup & Restore
- Automated daily pg_dump backups with point-in-time recovery (PITR) enabled on PostgreSQL.
- In disaster scenario, spin up standby database container and restore latest snapshot:
  ```bash
  psql $DATABASE_URL < latest_backup.sql
  npx prisma migrate deploy
  ```
